# Logic Prototype

用 terminal TUI 讓使用者手動驅動狀態模型。適合的問題類型是：商業邏輯、狀態轉換、資料結構，那種在紙上看起來合理，但實際操作一次才會發現問題的東西。

## 適用情境

- 「我不確定這個狀態機能不能處理先 X 後 Y 的邊界情況。」
- 「這個資料模型能不能表示⋯這種狀態？」
- 「我想先感受一下 API 介面應該長什麼樣，再動手寫。」
- 任何「想按按鈕看狀態改變」的情境。

若問題是「這個畫面應該長什麼樣」，選錯分支了，改用 `UI.md`。

## 流程

### 步驟 1：先把問題寫清楚

在 prototype 頂端的註解寫下正在測試的狀態模型，以及這個 prototype 要回答什麼問題。回答錯問題等於全部浪費，先把問題寫明，事後才能驗證答案。

### 步驟 2：選語言

跟著專案走，預設用 TypeScript + tsx（`pnpm exec tsx`）。若專案沒有明確的 runtime，問使用者。

### 步驟 3：把邏輯隔離成獨立模組

把真正在回答問題的邏輯放在一個純粹的介面後面，讓它之後可以直接移植進正式 codebase。TUI shell 是要丟掉的，邏輯模組不是。

依問題的性質選形狀：

- **純 reducer**：`(state, action) => state`。動作是離散事件、狀態是單一物件時適用。
- **狀態機**：明確定義狀態與轉換規則。「哪些動作在目前狀態下合法」本身就是問題的一部分時適用。
- **純函式集合**：對純資料型別做轉換，沒有隱含的當前狀態。
- **帶狀態的 class 或 module**：邏輯確實需要管理持續性內部狀態時才用。

選最符合問題的形狀，不是最容易接上 TUI 的形狀。邏輯模組必須保持純粹：不做 I/O、不寫 terminal 相關程式碼、不用 `console.log` 控制流程。TUI 呼叫它，不是反過來。

### 步驟 4：建立最小的 TUI

建立一個輕量 TUI，每次操作後清除畫面（`console.clear()`）並重新渲染整個畫面。使用者永遠看到一個穩定的畫面，不是不斷往下滾的 output。

每個畫面包含兩個部分，順序如下：

1. **當前狀態**，每個欄位一行，或整個物件格式化成 JSON。欄位名稱用粗體（`\x1b[1m`），次要資訊（時間戳、ID、計算值）用淡色（`\x1b[2m`），重置用 `\x1b[0m`。不需要額外引入樣式套件，除非專案本來就有。
2. **快捷鍵清單**，列在畫面底部：`[a] 新增  [d] 刪除  [t] 推進時間  [q] 離開`。

操作流程：
1. 初始化狀態，渲染第一個畫面。
2. 每次讀取一個按鍵，dispatch 給 handler 更新狀態。
3. 每次操作後清除並重新渲染整個畫面，不追加輸出。
4. 迴圈，直到使用者離開。

整個畫面要能在一個螢幕內呈現。

### 步驟 5：設定啟動指令

在 `package.json` 的 `scripts` 加入腳本：

```json
"prototype:order-state": "tsx src/orders/prototype/run.ts"
```

使用者只需 `pnpm prototype:[name]` 就能啟動，不必記路徑。

### 步驟 6：把操作權交給使用者

給使用者 run 指令，讓他自己操作。有趣的時刻是使用者說「等等，這不應該可以發生」或「我以為 X 應該不一樣」，那是**概念本身的 bug**，正是 prototype 要挖出來的東西。使用者想加新動作，就加，prototype 可以在操作過程中演進。

### 步驟 7：記錄答案

Prototype 完成後填寫旁邊的 `NOTES.md`。若使用者不在線，先把空殼建好，確保答案在 prototype 被刪掉之前被記錄下來。

## Anti-patterns

- **不寫測試。** 需要測試的 prototype 已經不是 prototype 了。
- **不連正式的 DB。** 除非問題本身就是關於持久化，否則用記憶體儲存。
- **不過度泛化。** 不要「如果之後要支援 X 怎麼辦」，prototype 回答一個問題就夠了。
- **不把邏輯和 TUI 混在一起。** Reducer 或狀態機裡若出現 `console.log`、prompt 或 escape code，它就無法移植了。TUI shell 保持薄薄的一層，只包在純邏輯模組外面。
- **不把 TUI shell 送進正式程式碼。** Shell 是為了手動操作而存在的，有價值的是它背後的邏輯模組。
