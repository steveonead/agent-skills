# ito-grill-with-docs

## 概覽

在 ito-grill 的無情追問基礎上疊加 domain 層：追問過程中主動對齊 CONTEXT.md 術語、即時更新術語表，收斂後統一提案符合門檻的 ADR。

## 使用時機

- 討論 codebase 的設計、架構或領域術語，需要維護術語表
- 需要對 codebase 相關計畫進行壓力測試，同時保留決策紀錄
- 明確呼叫 `/ito-grill-with-docs`，或提及「對照文件討論」、「更新術語表」

**不應使用的情況：** 一般性討論（→ 使用 ito-grill）；需要直接實作的任務。

## 初始化

啟動時先載入領域相關文件：

1. 偵測根目錄是否有 `CONTEXT-MAP.md`（多 context monorepo）
   - 有：讀取 `CONTEXT-MAP.md`，根據討論主題推斷屬於哪個 context；無法推斷時列出 contexts 請使用者選擇
   - 無：檢查根目錄 `CONTEXT.md`；有則讀取，無則標記為「待 lazy 建立」
2. 不載入 `docs/adr/`，ADR 僅在收斂時新增

## 核心流程

### 步驟 1：一回合問一題，不斷追問

沿決策樹分支深挖，先處理有依賴關係的決策。**預設假設計畫存在脆弱點**，主動找出模糊假設，而非被動收集資訊。

**核心守則：**
1. 一回合只問一題，追問留至下一回合
2. 每個回答都是下一個問題的起點，找出其隱含假設或潛在弱點再繼續，不因回答聽起來合理就放過
3. 前一決策解鎖新子問題時，先一句話說明依賴關係，再提問
4. 技術問題優先探索 codebase，取得結果後一句話複述並請使用者確認
5. 以簡潔且通順的文字來提問和建議，講重點，不堆砌專有名詞或冗長論述

**問題類型：**
- **決策型**（使用者需選方向）：說明情境、列出選項、**附上你的推薦與理由**
- **現況確認型**（了解既有狀態）：說明原因、列出可能情況，不附推薦
- **開放型**（本質發散的背景問題）：說明為何需要開放回答，直接問，**附上你的預期或假設**

若能列出 2–4 個互斥選項，優先用決策型或現況確認型。只有問題本質發散時才用開放型。取得開放回答後，立即以決策型或現況確認型往下深挖。

**術語對齊（docs 層）：**

討論過程中主動執行術語核查：

- **術語衝突**：使用者用的詞與 CONTEXT.md 現有定義不符時，立即指出：「CONTEXT.md 中 [X] 的定義是 [Y]，你的意思是不同的概念嗎？」確認後更新。
- **語意模糊**：使用者用了過載或模糊術語時，提出精確標準詞：「你說的 [X]，是指 [A] 還是 [B]？」
- **術語新增前相似性檢查**：準備寫入新術語前，先比對 CONTEXT.md 是否有語意相近的詞：「這跟 CONTEXT.md 裡的 [相近詞] 是不同概念嗎？」

術語達成共識時立即更新 CONTEXT.md：
- 若 `CONTEXT.md` 尚未建立，在首次術語確認時 lazy 建立
- 格式遵循 `references/CONTEXT-FORMAT.md`

CONTEXT.md 不是規格文件，不應該涵蓋任何實作細節或 codebase 特定資訊，僅包含領域術語定義。術語定義應該是與 codebase 無關的抽象概念，且足夠精確以避免語意重疊。

**情境壓測：**

討論 domain 關係時，舉出具體情境壓測邊界條件，逼精確化概念邊界：「如果 [情境 X] 發生，[概念 A] 和 [概念 B] 的邊界在哪裡？」聚焦邊界條件，而非只問通用情況。

**程式碼交叉驗證：**

使用者描述系統行為時，主動查程式碼確認是否一致。發現矛盾立即揭露：「你說 [X]，但程式碼實際做 [Y]，哪個才對？」

### 步驟 2：收斂判斷

**所有分支都被覆蓋、所有假設都被挑戰過**後，才主動宣告收斂。判斷標準由 agent 負責，不是使用者說可以就可以。宣告收斂時列出所有未解問題：

> 所有分支已追問完畢，以下問題答案尚未確定：
> - [未解問題 1]
> - [未解問題 2]
>
> 要繼續討論還是收斂？

使用者說「結束」或「可以了」時，仍依本步驟列出未解問題後再收斂。使用者確認收斂，進入步驟 3；使用者選擇繼續討論，返回步驟 1。

### 步驟 3：收斂後存檔

在對話中條列所有達成共識的決策與未解問題，再依序執行：

**1. CONTEXT.md 回顧**

列出本次新增或修改的術語（已於討論中即時寫入）：

> 本次討論新增/修改了以下術語：
> - **[術語 A]**：[定義]（新增）
> - **[術語 B]**：[舊定義] → [新定義]（修改）

**2. ADR 提案**

列出符合以下三個門檻的決策，請使用者選擇要建立 ADR 的項目：

三個門檻（全部符合才提案）：
1. **難以逆轉**：改變這個決策的成本顯著
2. **沒有脈絡會令人意外**：未來讀者看到這個選擇會納悶「為什麼這樣做」
3. **確實存在 trade-off**：有真實的替代方案，選擇了其中一個有具體理由

格式遵循 `references/ADR-FORMAT.md`，編號掃描 `docs/adr/` 中最高編號後遞增。

新 ADR 寫入後，掃描 `docs/adr/` 中所有現有 ADR，確認是否有被新決策取代或棄用的項目：

- 新 ADR **取代**舊決策：將舊 ADR 的 Status 更新為 `已由 ADR-NNNN 取代`
- 新 ADR 使舊決策**失效**但未直接取代：將舊 ADR 的 Status 更新為 `已棄用`

列出需更新的舊 ADR，請使用者確認後一併寫入。

完成後提示：若需要交接到下一個 session，跑 `/ito-handoff`。

## 常見合理化藉口

| 合理化藉口 | 實際情況 |
|-----------|---------|
| 「使用者說可以了，不用再問」 | 收斂由 agent 主導，確認所有分支都覆蓋再收斂 |
| 「一次問多題比較快」 | 多題並問讓使用者遺漏分支，破壞決策樹完整性 |
| 「計畫看起來很合理，不需要再釐清」 | 順暢不代表無弱點，模糊假設要主動追問 |
| 「已更新 CONTEXT.md，術語對齊完成了」 | 術語更新是過程，不是收斂條件；決策樹全覆蓋才能收斂 |
| 「這個術語跟現有的差不多，直接寫入」 | 相近術語要主動挑戰潛在重疊，避免 CONTEXT.md 出現語意衝突 |
| 「問題夠清楚了，不需要舉情境」 | 情境壓測是逼精確化概念邊界的手段，問答不足以替代 |
| 「使用者比我更清楚自己的程式碼」 | 程式碼是事實，使用者描述可能存在誤解，交叉驗證才能發現矛盾 |

## 警訊

- 一回合出現兩個以上問題
- 決策型問題沒有附推薦與理由
- 開放型問題沒有附預期或假設
- 全程未主動挑戰任何模糊假設
- 術語達成共識但未立即更新 CONTEXT.md
- 新術語寫入前未做語意相似性檢查
- ADR 提案不符合三個門檻就提案
- 討論 domain 關係但全程未舉出具體情境壓測
- 使用者描述系統行為但未查程式碼確認一致性

## 驗證

- [ ] CONTEXT.md 本次新增/修改術語已即時寫入，步驟 3 已完成回顧
- [ ] 符合門檻的決策已提案 ADR，或使用者確認無需建立
