# ADR 格式

ADR 存放於 `docs/adr/`，使用連續編號：`0001-slug.md`、`0002-slug.md`，以此類推。

`docs/adr/` 目錄採 lazy 建立，第一個 ADR 需要時才建立。

## 模板

```md
# {決策的簡短標題}

{1–3 句話：背景是什麼、我們做了什麼決定、為什麼。}
```

就這樣。ADR 可以只有一個段落。重點是記下「有這個決策」和「為什麼」，不是填滿欄位。

## 格式規則

- **多個理由用列點**，不用分號（`;`）壓縮成一行。兩個以上的理由就換列點。
- 列點以動詞或名詞起頭，不重複標題。

## 選用段落

只在能真正增加價值時才加入。多數 ADR 不需要這些。

- **Status** frontmatter（`提案中 | 已接受 | 已棄用 | 已由 ADR-NNNN 取代`）：適用於決策被重新檢視時
- **考慮過的選項**：只在被否決的替代方案值得記憶時才加
- **後果**：只在非顯而易見的下游影響需要被點出時才加

## 編號

掃描 `docs/adr/` 中最高的現有編號，遞增一後使用。

## 何時提案 ADR

以下三個條件全部符合才提案：

1. **難以逆轉**：改變這個決策的成本顯著
2. **沒有脈絡會令人意外**：未來讀者看到程式碼，會納悶「為什麼要這樣做？」
3. **確實存在 trade-off**：有真實的替代方案，選擇了其中一個有具體理由

決策容易逆轉就跳過，反正以後可以改。不會讓人意外就跳過，沒人會問為什麼。沒有真實替代方案就跳過，不過是做了顯而易見的事。

### 符合條件的決策類型

- **架構形狀**：「我們使用 monorepo。」「write model 採事件溯源，read model 投影至 Postgres。」
- **context 之間的整合模式**：「Ordering 和 Billing 透過 domain event 溝通，而非同步 HTTP。」
- **帶有鎖定成本的技術選型**：資料庫、訊息佇列、身份驗證服務、部署目標。不是每個套件，只有那些換掉要花很多很多精力的。
- **邊界與範疇決策**：「Customer 資料由 Customer context 擁有，其他 context 只透過 ID 引用。」明確的「不」和明確的「是」一樣有價值。
- **刻意偏離顯而易見路徑的選擇**：「我們用手寫 SQL 而非 ORM，因為 X。」任何合理的讀者會假設相反做法的情況，記錄下來能防止下一位工程師「修掉」刻意為之的設計。
- **程式碼看不出來的限制**：「因為合規要求，我們不能用 AWS。」「因為合作夥伴 API 合約，回應時間必須在 200ms 以內。」
- **否決理由不明顯的替代方案**：若評估過 GraphQL 最後選了 REST 且有深層原因，就記下來，否則六個月後有人還是會建議用 GraphQL。
