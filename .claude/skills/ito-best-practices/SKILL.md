# ito-best-practices

## 概覽

引導使用者為指定技術建立結構化 best practices skill，產出可直接使用的 `SKILL.md` 與 `references/` 規則目錄。

## 使用時機

- 使用者說「建立 X best practices skill」、「幫我建 X 的最佳實踐」或呼叫 `/ito-best-practices`
- 使用者有技術名稱、文件連結或粗略規則清單，想整理成結構化 best practices
- 需要為現有技術建立可供 agent 引用的規則集

**不應使用的情況：** 修改既有 best practices 規則、撰寫 PRD、建立非 best practices 性質的 skill。

## 核心流程

### 步驟 1：開場與素材收集

依序詢問，一回合一題：

1. 第一題：要為哪個技術建立 best practices？
2. 取得技術名稱後，第二題：是否有素材要帶入？（文件連結、現有規則清單，可選）

記錄回應做為候選規則的基底。

### 步驟 2：衝突檢查

檢查 `.claude/skills/<技術名稱>-best-practices/` 是否已存在：
- 若不存在，直接進入步驟 3
- 若已存在，詢問使用者：A）更新既有規則 或 B）從頭建立（內容全部重寫）
  - 選 A：讀取現有 `SKILL.md` 與所有 `references/*.md`，以現有規則做為步驟 3 的初版候選規則清單
  - 選 B：直接進入步驟 3，從零產出候選規則清單

### 步驟 3：候選規則產出

**優先檢查 ARGUMENTS**：若 ARGUMENTS 中包含搜尋意圖（如「搜尋」、「查」、「社群」、「參考資料」、「文件」），在產出候選清單前先執行對應查詢，以查詢結果為基底產出規則，不從自身知識直接回答。可用工具同步驟 4 的深挖工具。

根據使用者素材與本身知識，產出初版候選規則清單。

每條格式：
```
<類別前綴>-<規則名稱> — <一句話說明>
```

數量依技術複雜度彈性決定，不設硬性上下限。

### 步驟 4：討論循環

重複以下循環直到收斂：

1. **使用者標記** — 使用者指出要深挖、修改或刪除的規則
2. **深挖** — 對標記規則追問細節、範例、邊界條件。若使用者要求查詢，依需求選擇工具後摘要帶回討論，不主動搜尋：
   - **Exa**：搜尋技術 KOL 部落格與實戰文章
   - **Context7**：查閱官方文件，確認新版 API 的正確用法
   - **DeepWiki**：查閱 GitHub 專案文件與架構說明

   同樣工具也可用於驗證規則描述或程式碼範例是否與最新 API 一致。
3. **規則更新** — 納入討論結果，更新規則清單
4. **收斂判斷** — 當覆蓋足夠、無明顯空白時，主動提議：「規則覆蓋看起來已足夠（目前 N 條，涵蓋 [分類摘要]）。要進入草稿確認，還是繼續討論？」

### 步驟 5：草稿確認

在對話中展示摘要：
- 規則總數與分類列表（每個分類的規則數）
- 本輪新增、修改、刪除的規則（若為迭代）

使用者確認後進入步驟 6，否則返回步驟 4。

### 步驟 6：寫檔案

1. 讀取 `assets/output-skill-template.md`，填入技術名稱、分類、規則清單，寫出 `.claude/skills/<技術名稱>-best-practices/SKILL.md`
2. 讀取 `assets/rule-template.md`，依每條規則填入內容，寫出對應的 `.claude/skills/<技術名稱>-best-practices/references/<類別>-<名稱>.md`

## 規則格式規範

- **主體語言**：繁體中文
- **保留英文**：程式碼、專有名詞、常見技術術語
- **程式碼範例**：預設附 `❌ Bad` 與 `✅ Good`，僅在規則不易用程式碼示範時允許純文字（詳見「規則寫作規範」）
- **命名規則**：`<類別前綴>-<規則名稱>.md`，小寫 kebab-case

## 規則寫作規範

撰寫每條規則檔案時，遵循下列原則。

### 語言風格

- 通順、精準、不廢話的繁體中文，貼近**台灣工程師**日常用語
- 不使用破折號（`——`），以逗號或句號替代
- 不使用過度口語化的字眼（如「天書」、「一坨」、「神扯」、「暴雷」等），保持工程文件語感

### 內容處理

- **每條規則重新審視撰寫**，不直接照抄來源資料（包含官方文件、部落格、現有規則清單）
- **英文來源不照字面翻譯**，依上下文重新組織為自然中文。例如 `prefer composition over inheritance` 不譯成「偏好組合勝於繼承」，而是依語境寫成「優先用組合，避免繼承」
- 同義概念在規則集內統一用詞，避免一條寫「parse」、另一條寫「解析」

### 範例優先

- **預設每條規則都附上 `❌ Bad` 與 `✅ Good` 程式碼範例**
- 僅當規則本質不易用程式碼示範（如命名慣例、目錄結構決策、流程約定）時，允許純文字說明，並在規則檔案內註明原因
- 抽象文字說明放在程式碼範例之後，補充「為何這樣寫」，不替代範例本身

## 常見合理化藉口

| 合理化藉口 | 實際情況 |
|-----------|---------|
| 「使用者沒有標記問題，可以直接寫檔了」 | 需主動判斷覆蓋是否足夠，不等使用者先宣告完成 |
| 「只有技術名稱，沒辦法產候選清單」 | 技術名稱本身就是足夠的基底，本身知識可補足初版清單 |
| 「規則夠多了，不用問了」 | 數量不等於覆蓋，需確認分類是否完整、有無明顯空白 |
| 「ARGUMENTS 沒說要搜尋，所以直接產清單」 | ARGUMENTS 是使用者在呼叫時給的指示，同樣算使用者要求，必須在步驟 3 執行 |
| 「主動搜尋比較快」 | 步驟 4 討論中不主動搜尋，但 ARGUMENTS 明確要求的除外 |

## 警訊

- 未詢問素材就直接產候選清單
- ARGUMENTS 含搜尋意圖卻未在步驟 3 執行查詢，直接從自身知識產清單
- 步驟 4 討論中使用者未要求卻主動觸發 Exa、Context7 或 DeepWiki
- 草稿摘要未列分類，使用者無法評估覆蓋完整性
- 規則檔案命名未使用類別前綴
